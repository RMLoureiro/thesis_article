\begin{abstract}
	\noindent With Ethereum going through \textit{The Merge} and moving from a Proof-of-Work to a Proof-of-Work consensus
						it has oppened itself to a new range of attacks. One of this attacks was a bouncing attack on liveness that
						prevented the blockchain from finalizing new blocks, the Ethereum community then responded with a patch to fix
						this vulnerability. An article analyzing this vulnerability and subsquent patch has found that there is a new
						vulnerability on the patched protocol that results in the protocol only having probablistic liveness. The article
						only provides a theorethical analysis and pseudo-code which motivated us to implement Ethereum as described, the attack
						and subsquent patch in MOBS. We therefore provide imperical evidence to complement the theoretical analysis supporting the
						claims made on the article.
\end{abstract}

\section{Introduction}

Consensus and blockchain protocols are usually described with pseudocode and model checked with idealized languages that 
not reflect the implementations. Since validating correctness is very costly, before planning an
implementation, developers should test their ideas and prototypes. There is a lack of methodologies to develop,
evaluate, tune and replicate these protocols, opening a need for extensible and modular tools for consensus analysis and
experimental labs for rapid prototyping.
With this in mind MOBS was developed with the aim to give the ability to test and validate these protocols under different conditions and settings by 
changing the execution parameters, aiming to catch vulnerabilities or even logic errors before deploying changes to these protocols.
Since verification of protocols is very costly, developers can use MOBS to get confidence in their implementations
from experimentations first.

Consensus protocols are inherently complex to design and implement correctly.
In blockchain systems, where financial transactions and dynamic behavior are the primary features, protocol correctness is essential,
as even minor errors can lead to substantial financial losses and system malfunctions. One illustration of this is the transition of
Ethereum from a Proof of Work to a Proof of Stake consensus. This transition exposed the protocol to vulnerabilities that could be
exploited by bouncing attacks on liveness.
The chain is unable to be finalized as a result of this type of attack, as the primary selected chain in the fork
choice rule is perpetually hopping between two alternative branches.

Liveness in a blockchain protocol is defined as the ability to always finalize new blocks. These blocks in the
Ethereum protocol are finalized through a process called Casper FFG (Friendly Finality Gadget)~\cite{casper_ffg}, in combination with
the LMD GHOST (Latest Message Driven Greediest Heaviest Observed SubTree) fork choice rule~\cite{ghost_casper}.

The Bouncing Attack is an attack that prevents the chain from being finalized by making the main chain
selected in the fork choice rule continually bounce between two candidate chains. The attack leverages the fact that
candidate chains should start from the justified checkpoint with the highest epoch, and Byzantine nodes exploit this by
dividing honest validators opinions, justifying a new checkpoint after some honest validators already have cast their vote.

In~\cite{ethereum_analysis} this attack and with the Ethereum protocol are specified and analyzed along with the patch
implemented by the Ethereum community. In this article is also stated and formalized that the patch only provides probabilistic
liveness but no implementation is given. Providing an implementation in MOBS complements the article by producing an
executable, reproducible reference: it validates the paper's assumptions, uncovers implementation-level corner cases, and
allows empirical measurement of attack success rates and the patch's effectiveness under realistic network and Byzantine
conditions. This practical reproduction strengthens the article's claims by enabling repeatable experiments, quantitative
evidence, and clearer guidance for protocol implementers.

This document serves as a complement and provides more detailed information about our implementation and how it relates to the sdescription given in the article.

Here we show and detail our implementation in MOBS along with the re-creation of the Bouncing Attack, the patch proposed by the Ethereum
community and how this patch only provides probabilistic liveness.

\section{Implementation}

Our implementation was done in MOBS a simulator makes use of OCaml's \textit{modules} and \textit{functors} to
provide modularity and extensibility. MOBS adopts a \textit{Discrete-Event Simulation Model}
making the state of the system only change in discrete points in time when events occur.
These events are stored in a queue ordered with two main values:
\begin{itemize}
  \item \textbf{Timestamp:} This value dictates the order in which the events are
stored in the queue and is based on the simulator's internal clock. When getting
a new event the simulator will fetch from the queue the one with the smallest timestamp
and move its internal clock to match that event's timestamp.
  \item \textbf{Target:} The entity that should process this event.
\end{itemize}
Events are fetched from the queue until no more events remain or a predefined
stopping condition is reached.

For our implementation in MOBS we followed the description provided in pseudocode provided in~\cite{ethereum_analysis}. We focused on the
parts pertaining to the consensus mechanism and to allow a faithful replication of the results ignored some of the randomness mechanisms
that were described like choosing the member of the Proposers and the Validators committee. We also assumed that each attestation has a weight of 1
when the protocol was running for simplicity.

In our implementation~\ref{fig:mobs_receive_main} we continuously every node sends
a message to itself at the end of the main loop execution to execute the main code again. Also instead of extracting the logic of
\textit{prepareBlock()} and \textbf{\texttt{prepareAttestation()}} to their own methods we keep them explicit in the main code.

\section{Results}

Our implementation allowed us to recreate the scenarios presented in~\cite{ethereum_analysis} and validate the claims made in the article.
The first scenario we tested was a basic execution of the protocol without any Byzantine nodes to validate that the protocol
was able to finalize new blocks as expected.
To validate this execution we ran the simulation for a predefined amount of time and checked that new blocks were being finalized.
To help with this validation we logged every time a node finalized a new block and at the end of the simulation we used a python script
to parse the logs and check that a new block was finalized for each epoch.
\begin{figure}[H]
	\centering
	\includegraphics[width=4.5in, angle =0]{Figures/ethereum_correct_execution.png}
	\caption{Output from the log analyzer script for an Ethereum correct execution}
	\label{fig:ethereum_correct_execution}
\end{figure}

In our second scenario we implemented Byzantine behavior for some nodes in order to recreate the bouncing attack as described in the article.
This behavior would start at a predefined epoch and would make the Byzantine nodes split the honest validators opinions
by justifying a new checkpoint after some honest validators already have cast their vote.
We ran the simulation for the same amount of time as the previous scenario and checked that no new blocks were not being finalized.

\begin{figure}[H]
	\centering
	\includegraphics[width=4.5in, angle =0]{Figures/ethereum_incorrect_execution.png}
	\caption{Output from the log analyzer script for an Ethereum incorrect execution}
	\label{fig:ethereum_incorrect_execution}
\end{figure}

After in our next scenario we implemented the patch proposed by the Ethereum community to mitigate the bouncing attack. This patch would make nodes only consider
attestations up until a pre-determined slot when justifying a new checkpoint. This would give time for correct attestators to change their vote into the correct
block. After implementing this patch we ran the simulation again for the same amount of time and checked that new blocks were being finalized again even after the byzantine nodes
started their attack.

In our final scenario we wanted to validate the claim made in the article that the patch only provides probabilistic liveness. To validate this we changed the behaviour of the
byzantine nodes to simulate network lag. This would make the byzantine nodes justify a new checkpoint after the honest validators had already cast their vote
but before the pre-determined slot defined in the patch. This would make some honest validators change their vote to another chain and prevent finalization.
We ran the simulation for the same amount of time and checked that for some epochs no new blocks were being finalized.

\section{Conclusion}
This work provided an implementation of the Ethereum Proof-of-Stake protocol as described in~\cite{ethereum_analysis} along with the
bouncing attack and the patch proposed by the Ethereum community to mitigate this attack. Through our implementation
we were able to empirically validate the claims made in the article regarding the vulnerability of the protocol to the bouncing attack
and how the proposed patch only provides probabilistic liveness. Even though our implementation made some simplifications to the protocol
like assuming static quorums and every attestation having a weight of 1, the core logic of the protocol was preserved allowing us to validate the claims made in the article.

This implementation can be used as a guide for the implementation of other similar consensus protocols and blockchains. We present a way to use MOBS
to validate and test these protocols before deploying them in real world scenarios, allowing developers to catch vulnerabilities and logic errors early on diverse
scenarios.
